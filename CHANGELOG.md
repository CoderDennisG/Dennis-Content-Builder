## [0.7.0] - 2026-11-18

### Changed
- **Renamed to Denise** (2026-11-14). Folder `denise/`, bootstrap `denise.php`, namespace `Denise\`, constants `DENISE_*`, prefix `denise_`, text domain `denise`, REST namespace `denise/v1`, capability `denise_use_chat`, tables `{prefix}denise_*`, meta `_denise_field_backup`, debug log `denise-debug.log`, `DENISE_DEBUG` constant. `Denise\Support\Migration` carries existing tables, options, the capability, meta and cron over from the `dcb` names once (flag `denise_migrated_from_dcb`). Denise is becoming the site-wide assistant with pluggable skills; the content builder is its first skill family.
- **Admin menu says "Denise".** Top-level entry, page title and Settings page renamed from "Content Builder"; the sidebar entry is painted coral (`#cc6e4a`, hover `#b85e3d`) on every admin screen via an inline rule on the `admin-menu` stylesheet. Editor sidebar title, system-user display name and in-app copy follow.
- **Sidebar icon is a "D" monogram** (inline 20x20 SVG data URI in `ChatPage::ICON`), forced white over the coral entry with a CSS filter so the admin colour-scheme painter cannot grey it out.
- **Menu restructured.** Denise now has three entries: **Ask Denise** (`admin.php?page=denise`, new `Admin\AskPage`, a scaffold until the skills layer exists), **Content Builder** (`admin.php?page=denise-content-builder`, the former top-level chat page) and **Settings**. `AskPage` owns the top-level menu, icon and coral styling; `ChatPage` is a plain submenu now and gates its assets by the submenu hook.
- **New chat UI, shared by every surface.** `assets/chat.js` + `chat.css` rebuilt as one component (`deniseCreateChat`) with a header (D mark, title, subtitle), an empty state with suggestion chips, assistant replies rendered from Markdown (paragraphs, lists, headings, inline code, links, fenced code blocks with a Copy button), a coral user bubble, an animated status indicator, a conversations popover replacing the `<select>`, an auto-growing composer with a round send button, and a disabled state with hint. Mount options carry title/subtitle/greeting/intro/suggestions/placeholder; admin pages boot it from a `data-denise-boot` JSON attribute. Mobile-first CSS with coral tokens. Editor sidebar and front-end bubble mount it headless; the bubble launcher is now the D mark on coral.
- **Admin notices suppressed on Denise screens.** `AskPage::suppress_notices()` removes every `admin_notices` / `all_admin_notices` / `user_admin_notices` / `network_admin_notices` callback on the three Denise pages (hooked on `in_admin_header`), and a `denise-screen` body class hides notices injected later by JS.
- **Ask Denise works: skills.** New `Denise\Skills\Skill` contract (id, name, description, triggers, Markdown `knowledge()`, read-only `tools()` + `execute()`), `SkillRegistry` (built-ins + `denise_skills` filter, trigger-based selection, tool routing) and the first skill, **MEA Workshops** (`includes/Skills/MeaWorkshops/`): notes from its `card.md` plus the plugin's `docs/shortcodes.md` read live, and three lookups — `find_faculty`, `find_workshop`, `workshops_for_faculty`. New `Denise\Ask\AskOrchestrator` runs the same streamed tool loop as the builder against the skills, with the notes in a cached system block; new SSE route `POST denise/v1/ask`. Conversations gained a `kind` column (`builder` | `ask`, schema v3; `/conversations?kind=`) so the two histories stay apart. The streamed Anthropic turn moved out of `Orchestrator` into `Denise\Ai\Streamer`, shared by both loops. Settings model list gained Claude Opus 5.5, Sonnet 5.5 and Haiku 5.5.
- **Replies stream for real, and Ask is faster.** New `Denise\Ai\ClientFactory` + `StreamingTransport`: the SDK's discovered Guzzle client buffered every response, and even with `stream => true` the SDK's 8 KB reads blocked until full, so text reached the browser only when a turn ended. Now each read is capped at 256 bytes and tokens appear within about a second. Ask Denise gets its own model setting (`ask_model`, default Claude Sonnet 5.5, new dropdown in Settings) and runs at `effort: low` on models that support it. The MEA Workshops notes now carry compact faculty and workshop indexes (cached 10 min), so name questions answer in one turn instead of a tool round trip. `Streamer` emits a `usage` event (input, cache read/write, output, time to first token) per turn.
- **Front-end launcher moved to the admin bar.** The floating corner bubble is gone. A "Denise" item in the toolbar (coral D) opens the chat panel on a front-end singular view of a post type activated in Settings → Post Types that the user can edit; elsewhere it links to the chat page in wp-admin. `Frontend\Bubble` became `Frontend\Launcher`; the panel drops down under the toolbar; `#denise-chat` links and `window.Denise.open()` still open it. Nothing renders for anonymous visitors or on non-activated post types. A second gate only offers the toggle on content built with Elementor or the block editor (or still empty on a block-editor post type); classic-editor and Thrive Architect pages get the plain link to the chat page instead.
- **Front-end panel: lower-left, draggable, remembered.** The panel now opens in the lower-left corner (full width at the bottom on phones). From 783px it can be dragged by its coral header; the position is saved in `localStorage` (`denise.panel.pos`), restored on the next open and clamped to the viewport and below the toolbar on resize. `window.Denise.resetPosition()` clears it. Theme typography no longer leaks into replies: `bubble.css` pins font family, size, line height and letter spacing on paragraphs, lists, links and headings inside messages.
- **Denise inside the Elementor editor: live edits, no drafts.** Third surface (`Admin\ElementorEditor`, hooks `elementor/editor/after_enqueue_scripts` + `elementor/editor/footer`): the same panel mounts in the editor window (corner button opens it, defaults lower-right, position stored under its own key). A bridge (`assets/elementor-editor.js`) sends the live document with every message (ids, types, text settings, current selection; `Ai\EditorContext` validates and caps it, nothing is stored) and applies Denise's edits through the editor's command bus (`document/elements/settings|create|move|duplicate|delete`): instant in the preview, in the undo history, saved only when the person clicks Update. In editor mode the tools never write to the database: `read_elementor_page`/`read_elementor_element` answer from the snapshot; `update_elementor_element` (settings only), `add_elementor_widget`, move/duplicate/remove record an `editor` action the panel relays; styles, classes and `add_elementor_elements` are refused with a hint. Plain settings become Elementor's typed props through Elementor's own resolver (`Adapters\ElementorProps`, V3 widgets stay plain, so legacy widgets are editable live too). The snapshot goes in as the last system block, after the cached notes, so it never breaks the prompt cache. `deniseCreateChat` gained a `context` option (extra request fields per message). Chat route accepts `editor`. The bridge's `apply( action, done )` reports each outcome through a callback (synchronous for element edits, later for template inserts); the panel logs every relayed edit to the console (`[Denise] editor edit`) and keeps the last ten in `window.Denise.lastEdits()`.
- **Saved templates: lookup shipped, insertion parked (Security/Permissions).** `find_elementor_template` looks up "My Templates" by name (id, title, type, insertable; theme parts such as headers, footers and loop items are listed but not insertable) and `insert_elementor_template` inserts one into the page open in the Elementor editor at the root, optionally at an index. New `Adapters\ElementorTemplates` reads the local library source only (published templates, or drafts the user can edit) and validates the type. The browser then drives Elementor's own library flow (`library/open` with `importOptions.at`, then `library/insert-template` with a template model): Elementor fetches the content, shows its "how to apply styles" dialog when the template carries global styles, closes the library and imports, exactly as clicking Insert does. The bridge watches the command bus (`run:after`) and reports success when `document/elements/import` ran for that template, or failure when the library closed without it. Outside the editor the insert tool refuses with a hint to open the page in Elementor. **Parked:** in Dennis's browser neither relay inserted anything and nothing surfaced in the console or network, so `insert_elementor_template` is switched off behind `Tools::TEMPLATE_INSERT_ENABLED` (not offered to the model, refuses if called) and the prompt tells Denise to send people to Add Template → My Templates → Insert instead. See docs/ROADMAP.md backlog.
- **Workshop intake: a workshop from the client's document (Security/Permissions).** New skill `Skills\WorkshopIntake` (notes in `knowledge.md`: the doc → ACF mapping, the doc → "WS Guest Faculty Template" section mapping, the report-don't-invent rules, the two-step summary-then-build flow) with one pure tool, `convert_agenda` (`AgendaConverter`: day headings + timed lines → the `[mea_workshops action="workshop_agenda"]` block, with a day-one vs `start_date` check). New content tools `create_elementor_draft_from_template` (empty draft + template copied onto it via `Adapters\ElementorTemplates::apply_to()`, Elementor `Document::save()`, fresh ids, page settings minus post-level keys; returns the root sections with ids and editor names) and `apply_elementor_template` (drafts only, confirm when a layout exists). RULES.md rule 6 scoped exception. **Legacy widgets on drafts:** Elementor's manage-elements refuses V3 widgets (`elementor_v3_not_supported`) and reads their settings as empty, and the workshop template's narrative is all V3 (text editor, icon list, shortcode). New `Adapters\ElementorLegacy`: `read_elementor_element` now fills in V3 content settings from the stored data (`legacy: true`), and `update_elementor_element` writes V3 text keys and repeater rows (icon list rows keep their icon and id) on a DRAFT through `Document::save()`; refused on published posts and for style/classes.
- **Field writer handles repeaters, groups and post references (Security/Permissions).** `Content\Fields` now writes `repeater` (rows keyed by sub-field key, validated per sub-field, read-only sub-fields dropped), `group`, `post_object`, `relationship` and `page_link` (existing posts of the allowed types; list or single by the field's "multiple"). The schema reports `post_type` and `multiple` for reference fields. `update_fields` refuses to replace existing repeater rows until `confirm_replace` is passed after the person agreed (`Fields::replacements()`); RULES.md rule 11.
- **Text edits change only text, and legacy widgets redraw at once (editor mode).** Dennis's test: asking Denise to change an icon list's text replaced the rows wholesale, so the icons fell back to defaults, and legacy widgets only showed the new text after a click. The bridge now treats legacy (V3) widgets the way the panel does: list rows (`icon_list`, `tabs`, `slides`) are changed through their own repeater-row containers with text keys only (`_id`, icons and images untouched), extra rows are inserted as clones of the last row via `document/repeater/insert`, surplus rows removed via `document/repeater/remove`, scalar keys go through `document/elements/settings`, and the widget view is asked for a full `renderHTML()` afterwards. The prompt and the tool description now say a text change passes text keys only.
- **Toolbar mark no longer crooked.** Core styles toolbar icons with a three-id selector (dashicons font, 4px padding), which outranked Denise's rule: the coral circle was 18 × 26px, clipped by the bar, with a serif fallback "D". The letter now sits in an inner span (`.denise-ab-mark`) with its own font and size; the `.ab-icon` is a centred 18px box on desktop and core's 52 × 46px cell on phones.
- **No stray corner button on the front end.** bubble.js ran at footer-scripts time, before WordPress prints the admin bar, so it never found the "Denise" toolbar item and showed the corner "D" meant for builder editors next to it. The panel now boots on DOMContentLoaded (immediately when the document is already parsed), so the toolbar item is the only launcher on the front end and gets its open state.
- **Editor-mode failures are no longer silent.** Elementor's command bus swallows exceptions (it logs them and returns null), so a relayed edit that threw looked applied. The bridge now captures the logged error during the synchronous `$e.run` call, treats a null result as failure, verifies that an import actually created elements, shows the message in the panel, and sends the failures with the next message (`editor.failures`, capped at 5 × 300 chars); `Ai\EditorContext` prints them as "EDITS THAT FAILED" in the live-state block, and the prompt tells Denise that an ok tool result only means the edit was handed over.
- **Front-end panel: history and new-chat buttons in the header.** `deniseCreateChat` accepts `actionsHost`, an element that adopts the history / new-chat buttons and the history popover; the chat then renders no head of its own. The front-end panel passes its coral header, so the toolbar row is gone and the thread gets that height. The icons go white on the header; the popover drops below it. The chat's design tokens are now also declared on `.denise-bubble-panel` so the popover keeps its colours outside `.denise-chat`.
- **Builder gate enforced in the tool layer (Security/Permissions).** `Profiles::editor_of()` classifies a post as `elementor`, `blocks`, `thrive` or `classic`; `Profiles::is_supported_build()` is the gate shared by the front-end launcher and the tools. `read_content` and `update_content` now refuse Thrive Architect and classic-editor posts with a message the model passes on to the user (the Elementor tools already require the Elementor flag). `list_content` reports `editor` and `editable` per item, and the system prompt tells Denise up front when the open page cannot be edited. `update_fields` is not gated, since ACF values render independently of the builder. RULES.md rule 9.
- **Elementor edits to published pages are pending drafts.** Elementor's `manage-elements` keeps a published or private page live and writes changes into the current user's autosave revision; they go live when someone clicks Update in the Elementor editor. Denise now says so in every edit result (`note`), the action card reads "Draft saved, publish in Elementor", the front-end bubble offers "Open in Elementor" instead of a reload hint, and `read_elementor_page` / `read_elementor_element` read from that pending draft when it is newer than the page (`reading` field), so consecutive edits build on each other. Draft pages are written directly.
- **Elementor editing moved to Elementor's own abilities; EMCP Tools no longer needed.** Elementor 4.3+ ships an abilities module (`elementor/get-page-structure`, `manage-elements`, `build-composition`, `get-widget-schema`, `list-widget-schemas`, …) that takes plain settings and validates against each widget's schema, which fixes the "Settings validation failed. title: invalid_value" dead end on atomic widgets. New `Adapters\ElementorAbilities` registers them in-process on `wp_abilities_api_init` when Elementor's MCP switch is off (nothing is exposed externally) and runs them. The Elementor tools were rewritten on top: `read_elementor_page`, `read_elementor_element` (content in the writable shape), `update_elementor_element` (plain settings + CSS string + classes via manage-elements), `add_elementor_widget`, new `add_elementor_elements` (build-composition XML for whole sections), `move_elementor_element`, new `duplicate_elementor_element`, `remove_elementor_element`. `ElementorAdapter` now builds new pages as a composition (atomic e-flexbox / e-heading / e-paragraph / e-button / e-image / e-divider) instead of EMCP's factory. `Model::sanitize_css()` added; `Model::INLINE_HTML` is public. The EMCP Tools plugin can be deactivated once verified.
- **Skill notes live in the plugin they describe.** The MEA Workshops skill now reads `mea-workshops/docs/card.md` live (next to `docs/shortcodes.md`) instead of a bundled copy, so one file serves Denise, Claude Code sessions and production. Pattern for every future skill: the plugin ships `docs/card.md` + `docs/shortcodes.md`; Denise reads them where they are.
- **Settings page restyled in the MEA palette** (forest, teal, coral, cream, sand, gold, sage from the site's Elementor kit): forest header band with the D mark, cream panel, rounded cards with sand borders, coral tab underline and primary buttons, pill buttons, warm form controls. Colours reach the WordPress components through the `--wp-components-color-accent` custom properties. The chat's neutrals moved to the same cream and sand so both screens match.
- **One Denise.** Ask Denise and the Content Builder are merged into a single assistant: one chat page (`Admin\DenisePage`, menu "Denise → Chat"), one orchestrator (`Ai\Orchestrator` runs the content tools and every skill's lookup tools, with the skills' notes as a cached block), one prompt (editor-first answering rules + a "when to act" rule: questions get answers, drafts only on request), one model setting (default Claude Sonnet 5.5) and one history (`kind` column kept but no longer used for filtering). Retired: `Ask\AskOrchestrator`, `POST denise/v1/ask`, `Admin\AskPage`, the Content Builder submenu, the `ask_model` setting. The editor sidebar and front-end bubble are post-scoped views of the same assistant.
- **The Content Builder knows the skills too.** When a builder conversation touches a skill's subject (trigger match), the same reference notes Ask Denise uses are appended as a cached system block, with a clause on placing shortcodes as paragraph text. No match, no notes. `SkillRegistry::select()` gained a `$fallback_all` flag (Ask: no match loads all; builder: no match loads none).
- **Delete a conversation from the history list.** Trash button on each row of the Conversations popover (shows on hover, asks to confirm); `DELETE denise/v1/conversations/{id}` removes the thread with its messages and audit rows, owner only. Deleting the open thread resets the chat.
- **Fixed: reopening a conversation that contained bold text hung the page.** The Markdown renderer shared one global regex across recursive calls, so the inner call reset the outer one's position and it looped forever. Each call now clones the regex. `window.deniseRenderMarkdown` is exposed for tests.
- **Assets are cache-busted by file time** (`Plugin::asset_version()`), so script and style edits reach browsers without a version bump.
- **Ask and Content Builder histories are separate.** Every builder mount (admin page, editor sidebar, front-end bubble) now requests `kind=builder`, the Ask page `kind=ask`, and the `/conversations` route treats a missing kind as builder.
- **Conversation history, per user, done properly.** Titles are generated by one Haiku 5.5 call after the first answer has been sent (`Content\Titler`, `titled` flag, schema v4) instead of the first sixty characters of the question. Only the newest 24 (Ask) / 30 (builder) messages go to the model, trimmed to start on a plain user message so tool calls stay paired; the full thread stays stored. The Ask page reopens your most recent conversation from the last 24 hours. A daily `denise_retention` cron deletes conversations untouched for 90 days (`denise_retention_days` filter, 0 keeps everything) with their messages and audit rows.

### Changed
- **Sectioned page structure.** The assistant is now instructed to analyze content and divide a page into logical sections (each wrapped in a `group`) instead of emitting one flat list. The Elementor adapter renders each top-level `group` as its own full-width section container (siblings), and collects loose top-level elements into their own section — so pages read as distinct bands rather than a single stack. Builder-agnostic: Gutenberg renders the same sections as groups.
- **Named sections.** A `group` now carries an optional `label` (the assistant sets a short name per section). The Elementor adapter writes it to the container's `_title`, so sections show as "Hero", "Pricing", etc. in Elementor's Structure/Navigator panel instead of generic "Container".

### Added
- **Developer debug log.** Define `DENISE_DEBUG` truthy (e.g. in wp-config.php) to append the exact JSON flowing through the assistant — each tool's input and result, plus the Elementor element tree the adapter builds — to `wp-content/uploads/denise-debug.log`. Off by default; writes nothing unless enabled. New `Denise\Support\Debug`.
- **Front-end Denise chat bubble.** A floating chat launcher on the live page that mounts the same chat UI scoped to the post being viewed — the practical way to talk to Denise about an Elementor page (Elementor's editor has no Denise sidebar). Strictly gated: renders only for logged-in users with the chat capability who can edit the current post, on assistant-eligible singular views; never shown to anonymous visitors. After an edit it shows a "reload to see changes" hint (the front end doesn't live-refresh). New `Denise\Frontend\Bubble` + `assets/bubble.{js,css}`; reuses the shared chat core (`ChatPage::enqueue_chat_core()` is now public/static).

- **Elementor as a per-post-type builder (experimental).** Each post type now has a "Build new content with" choice in its settings popup: the block editor (default) or Elementor. When Elementor is selected, the assistant's new drafts are created as real Elementor pages (editable in the Elementor editor), while the AI still only emits the neutral content model — a new `ElementorAdapter` maps that model to Elementor widgets.
  - The adapter reuses the **EMCP Tools (elementor-mcp)** plugin's element factory + data layer in-process (no MCP/HTTP) so Elementor data is built and saved through Elementor's own document API. The option only appears when Elementor + EMCP Tools are both active; otherwise it falls back to the block editor.
  - Scope this release is **create-only**: reading/editing existing Elementor pages from chat is not supported yet and is refused with a clear message.
  - **Explicit chat override:** the per-type default is honored unless the user explicitly asks for a builder in chat ("use Elementor" / "use the block editor"), which wins. Implemented via an optional `builder` parameter on `create_draft`; the system prompt only mentions it when Elementor is available.
  - **Richer rendering:** containers now stretch their children to full width with real padding/gap (no more narrow centered stack); unordered lists render as Elementor's icon-list (check icons) rather than a plain bulleted text box; columns/groups get sensible spacing. Same neutral model — Gutenberg output is unchanged.
  - **Per-block override ("dictate the widget").** The mapping still chooses a sensible widget by default, but the user can now ask for a specific Elementor block in a specific spot. The assistant emits a `{type:"widget", widget, settings}` element that the Elementor adapter passes straight to EMCP's element factory — so the *entire* Elementor widget catalog is reachable, not a hand-maintained subset. Other builders ignore a `widget` element.
  - Two read-only discovery tools (Elementor only): `list_elementor_widgets` and `get_elementor_widget_schema`, thin in-process wrappers over EMCP's `list-widgets` / `get-widget-schema` abilities, so the assistant fills override settings from the real widget schema instead of guessing.
  - `widget` settings are treated as untrusted input: recursively sanitized (wp_kses_post + JS/VBScript-URI stripping, depth/breadth caps) before save.
  - **Editing existing Elementor pages (in place).** Denise can now read and modify Elementor pages, not just create them. Editing happens by element ID against the live Elementor tree (via EMCP's editing abilities) — never round-tripped through the neutral model — so existing styling and unmodelled widgets are preserved. New Elementor-only tools: `read_elementor_page`, `read_elementor_element`, `update_elementor_element` (partial-merge), `add_elementor_widget`, `add_elementor_container`, `move_elementor_element`, `remove_elementor_element`. The editor sidebar detects an open Elementor page and routes Denise to these tools; `read_content`/`update_content` refuse Elementor posts (they'd flatten the design). Edits are undoable via Elementor's own revisions. Edit-tool settings are sanitized as untrusted input, and the allowed EMCP surface is recorded in docs/RULES.md (content editing only — no globals, code, or post deletion).

### Changed
- `BuilderAdapter` contract gained `insert_meta()` and `persist()` so a builder can own how content is stored (post_content for Gutenberg, `_elementor_data` meta for Elementor). `create_draft` now resolves the adapter from the post type's builder setting.

## [0.6.0] - 2026-06-13

### Added
- Custom fields (ACF + native registered meta). The assistant can read and fill a post type's custom fields, scoped to an admin allowlist in the post-type popup.
  - **Discovery** is recursive: ACF field groups (incl. nested repeater/group/flexible-content sub-fields and choices) plus `register_post_meta` keys, surfaced as a checklist with type badges.
  - **Reading** covers the full field tree, including complex types, today.
  - **Writing** is enabled for the reliable types this release — text, textarea, wysiwyg, number, email, url, select/radio/checkbox/button-group, true/false, date/time, color — validated per type (choices checked, values sanitized). Complex fields (repeater, group, flexible content, image, file, relationship, post object) are read-only for now and reported as such to the model.
  - Two new AI tools: `read_fields` and `update_fields`. ACF values are written via `update_field`; native meta via `update_post_meta`.
  - **Undo for meta:** prior field values are snapshotted to `_dcb_field_backup` before any write, since WordPress revisions don't cover meta.
- New `dcb/v1/fields` endpoint backs the settings checklist.

### Notes
- Writing complex/nested field types (repeaters, flexible content) and setting media/relationship fields by searching existing items is the next phase — the schema engine already handles the full tree, so it's enablement, not a rebuild.

### Added
- Scheduled auto-creation, per post type: pick specific weekdays and a time (e.g. Mon/Wed/Fri at 6:00 PM) in the type's popup, give it a standing brief, and the assistant creates a new item on that schedule. Uses precise self-rearming timed events in the site timezone (exact under a real server cron such as WP Engine).
- "Run now" button in the popup to fire a scheduled type immediately (testing, and for environments where cron doesn't fire locally).
- Scheduled runs execute headless as a dedicated, plugin-provisioned "Content Builder" system user, attributing automated drafts to it; every run is audit-logged.
- Per-type **auto-publish** option: a scheduled run may publish its result automatically. Off by default.

### Security
- Documented the auto-publish exception in docs/RULES.md: the `create_draft`/`update_content` tools still only ever draft and the interactive chat can never publish; publishing happens only in the scheduled path, only for types an admin explicitly opted in, as a step after the model produces the draft.

### Notes
- Custom-field (ACF/meta) editing moves to v0.6.0.

## [0.4.0] - 2026-06-13

### Added
- Post type profiles: each post type gets its own behavior from one shared model — there is no separate "AI" per type, just a per-type configuration.
  - **Eligibility allowlist** — choose which post types the assistant manages; the editor sidebar is hidden and creation refused on the rest (defaults: pages and posts).
  - **Writing guidance** — per-type instructions/persona injected into the system prompt (a Product writes differently from a Blog post).
  - **Allowed blocks** — restrict each type to a chosen subset of blocks; enforced structurally at save (`Model::sanitize_elements`), not just suggested.
- New "Post Types" tab on the settings page (wp-components TabPanel) to edit all of the above.
- Profile rules are enforced across every entry point: `list_content`/`read_content`/`create_draft`/`update_content` all respect eligibility and per-type block limits, using each post type's own capability.

### Notes
- Custom-field (ACF/meta) editing is intentionally deferred to v0.5.0; field-based types show a note and still get block + guidance support.

### Changed
- Settings page rebuilt on WordPress's bundled `@wordpress/components` (Card, TextControl, SelectControl, CheckboxControl, Notice) for a native, modern look — no build step and no new dependency. It now reads/writes through a new `dcb/v1/settings` REST endpoint (manage_options) instead of an `options.php` form. Scope is the settings page only; the chat and editor sidebar are unchanged.

## [0.3.0] - 2026-06-13

### Added

- Conversations are scoped per post in the sidebar (each page has its own history); the admin chat page still shows everything.

## [0.2.0] - 2026-06-13

### Added
- Live progress streaming: `/chat` now answers as a Server-Sent Events stream — assistant text arrives token by token and tool steps show as status updates ("Writing your draft… 2,400 characters").
- Conversation persistence: conversations and messages are stored in custom tables; previous conversations can be resumed from a picker on the chat page.
- Audit log: every AI tool invocation is recorded (user, conversation, tool, post, detail).
- `dcb_use_chat` capability gates the chat UI and REST routes; role checkboxes in Settings control who gets it (administrators always do).
- PHPCS with the WordPress Coding Standards ruleset (`phpcs.xml.dist`); codebase passes clean.

### Changed
- The browser no longer round-trips Claude message history; the client sends only `{conversation_id, message}` and the server owns state.

### Added
- Project planning documents: README, architecture, roadmap, rules, versioning policy (2026-06-13).
- Working prototype (vertical slice, 2026-06-13):
  - Settings page with write-only Anthropic API key, model picker, and connection test.
  - Neutral content model with strict server-side sanitization of AI output.
  - `GutenbergAdapter` — neutral model ⇄ core block markup, round-trip verified against the WP block parser; unknown blocks preserved as opaque raw elements.
  - AI orchestrator running the Claude tool-use loop server-side (official `anthropic-ai/sdk` ^0.7) with a code-defined tool allowlist: `list_content`, `read_content`, `create_draft`, `update_content`, `search_media`.
  - REST API `dcb/v1` (`/chat`, `/test`) with capability-checked permission callbacks.
  - "Content Builder" admin chat page (drafts only — the AI cannot publish or delete).

### Changed
- Replaced the WPPB boilerplate with a PSR-4 `DCB\` structure; plugin version reset to 0.1.0 per docs/VERSIONING.md.
